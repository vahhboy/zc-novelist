# 恢复手册 · 卡住类型诊断与重派指令模板

## 一、先诊断，再动手

判定"卡住"之后，**先花 30 秒判断卡在哪一类**。不同类型的最佳恢复动作完全不同，
选错动作只会在同一个地方再卡一次。

### 诊断线索清单

按顺序找证据（都能从 `check` 输出 + 后台任务输出里拿到）：

1. `last_note` 是什么？最后一条进展描述停在哪一步
2. `artifacts` 有没有增长？长了说明在推进，只是慢
3. `beats` 次数 vs 已用时长 —— 有心跳但无产物 = 空转；0 心跳 = 一开始就卡
4. 后台任务最近的输出里有没有**重复出现的失败命令 / 报错**
5. 任务是否在等外部资源（网络请求、文件锁、用户确认、子代理回复）

### 卡住类型 → 首选动作

| 类型 | 典型证据 | 首选 | 次选 |
|---|---|---|---|
| **A. 单纯慢** | 有心跳、产物在涨、只是慢 | 什么都不做，继续等 | 超时后 L0 轻推 |
| **B. 输入过大** | 一开始就卡，或处理到某个大文件后卡 | L2 拆分输入 / 先做摘要再处理 | L1 重启 + 限制输入范围 |
| **C. 指令含糊** | 反复产出方向不对的东西、或反复追问式输出 | L1 用更明确的输入输出契约重派 | L2 拆成小步 + 明确每步产物 |
| **D. 工具/命令失败循环** | 同一条命令反复失败、报错重复出现 | L2 换工具或换参数重派 | L1 重启 + 明确禁用失败路径 |
| **E. 等外部资源** | 卡在下载、API、锁、等待回复 | L2 离线降级（跳过该资源，用已有材料） | L4 跳过该节点 |
| **F. 角色/任务不匹配** | 同一角色在不同子任务上反复卡 | L3 换角色接管 | L2 拆得更细 |
| **G. 死循环 / 空转** | 心跳在打但进展描述重复（SPIN） | L1 重启 + 明确"不要重复 X" | L2 降 `max_turns` 强制收敛 |
| **H. 上下文/记忆溢出** | 长任务后期开始胡言乱语或失忆 | L1 带 checkpoint 重启（新上下文） | L2 拆分 |

诊断不清时：**按 L0 轻推起步**，它成本最低且能拿到新信息（"你在做什么"的回答往往直接暴露类型）。

## 二、各级别的标准动作

### L0 · nudge 轻推

不停任务，只发一条追问。适用于后台子代理（`SendMessage`）或再取一次 `TaskOutput`。

```
请用一句话报告：
1) 你当前进行到哪一步
2) 已产出哪些文件
3) 下一步准备做什么
4) 有没有在等待什么（网络、文件、其他角色）
只回这四点，不要继续干活。
```

判断：宽限期（默认 60s）内有回复 → `beat` 记录，回到正常轮询；无回复 → 升 L1。

### L1 · restart-with-checkpoint

停掉旧任务（`TaskStop`），用**新上下文**重新派发同一角色，必须带 checkpoint。
新上下文很关键 —— 类型 H（上下文溢出）和 G（空转）都靠它解决。

### L2 · degrade-and-split

同一角色，但**缩小契约**：把节点拆成 2-3 个子任务逐个派、降低 `max_turns`、
换更快的模型、去掉非必要工具、限制输入规模。

### L3 · substitute-role

换人。团里另一个角色接手，或 team-lead 直接执行。**产物必须标注降级**。

### L4 · skip-and-escalate

`resolve --outcome skipped --note "<原因>"`，流水线继续跑其余节点，
最终报告里列出缺口，并在回复用户时**明确说明**哪部分没做、为什么、需要用户怎么决定。

## 三、重派指令模板

把下面模板里的占位符填实。**不要省略 checkpoint 段** —— 那是重派和裸重跑的唯一区别。

### 通用骨架（L1）

````
你是 <专家名> 团队里的 <角色名>，负责 <该节点的职责>。

## 背景
这次整体任务：<run 的 task 描述>
你上一次执行在 <卡住时长> 前停止了，需要带着已有成果继续，不要从头开始。

## 已经完成（checkpoint）
- <已完成项 1>
- <已完成项 2>
已产出文件：
- <artifact 路径 1>
- <artifact 路径 2>

## 卡住的位置
上一次停在：<last_note>
判断原因：<诊断类型，如"输入过大 / 指令含糊 / 工具失败循环">

## 本次只做这些（不要扩大范围）
1. <剩余的下一步，拆到最小可执行>
2. <再下一步>

## 硬性约束
- 不要重复 <已经做过的事>
- 不要 <导致上次卡住的动作，如"不要一次性读入全部章节">
- 每完成一个可见进展就写一次中间产物到文件，便于外部确认你在推进
- 只输出本次结果，不需要重述已完成部分

## 交付格式
<明确产物：文件路径 / 章节 / 字段>
````

### L2 拆分版（在骨架上追加）

````
## 范围收缩
本节点已拆成 3 个子任务，**本次只做第 1 个**：
- 子任务 1（本次）：<...>
- 子任务 2（下次派发）：<...>
- 子任务 3（下次派发）：<...>

## 额外约束
- 输入限制：只处理 <具体范围>，其余一律跳过
- 步数上限：最多 <N> 步，到点就把当前结果落盘并交付
- 禁用：<上次失败的工具/命令>
````

### L3 换人版（在骨架上改写开头 + 追加）

````
## 角色调整说明
本节点原由 <原角色> 承担，多次尝试未推进。现由你（<新角色>）接手。
你的视角与原角色不同 —— 请**用你自己的方法**达成同样的交付目标，不必沿用原角色的流程。

## 降级说明
本次产物将标注为「降级交付」，允许覆盖度和深度低于原角色标准，
但必须明确写出哪些部分因换人而未覆盖。
````

## 四、连环卡住的兜底

如果一个 run 里**多个节点**都卡住，通常不是节点问题而是**上游问题**：

| 现象 | 可能根因 | 处置 |
|---|---|---|
| 全部节点同时卡 | 外部资源不可用（网络/服务/配额） | 停 run，向用户报告，等资源恢复 |
| 后续节点全部空转 | 前序节点没产出，下游没有输入 | 检查 `--depends-on` 链，先修前序 |
| 同一类型节点反复卡 | 该类型任务与当前专家能力不匹配 | L3 换角色 + 向用户说明能力边界 |
| 重试预算普遍耗尽 | 任务定义过大 | 停 run，与用户重新切分任务范围 |

任何时候，**用 `AskUserQuestion` 把选择权交回用户都比闷头重试好**。
尤其是：跳过 vs 换人 vs 缩小范围 —— 这三类决定影响交付质量，用户有权知道。
