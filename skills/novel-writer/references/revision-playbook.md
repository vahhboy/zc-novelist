# 修订手册 · 从修改建议到剧情调整

改稿最贵的不是写字，是**改完之后发现还有五个地方没跟着改**。这份手册解决两件事：
改之前算清影响面，改之后同步干净。

---

## 一、先给建议分类

收到一条修改建议，先判断它属于哪一类 —— 类别决定工作量。

| 类别 | 例子 | 影响范围 | 典型工作量 |
|---|---|---|---|
| **L1 文字层** | 这段节奏拖了、对白不像他 | 单章局部 | 只改本章，不动台账 |
| **L2 章节层** | 这章结尾钩子不够强、信息投放太密 | 单章整体 | 改本章，节拍可能微调 |
| **L3 设定层** | 战力体系崩了、某个规则前后矛盾 | 全局 | 改 `worldbuilding.md` + 所有涉事章节 |
| **L4 剧情层** | 让沈青别死、把揭晓提前十章 | 多章 + 时间线 + 伏笔 | **必须做影响面分析** |
| **L5 结构层** | 换视角、换主角动机、重排卷序 | 全稿 | 等于重做大纲，先与用户确认 |

**只有 L1 可以立刻动手。L2 要过一遍节拍，L3-L5 必须先出方案给用户确认。**

---

## 二、影响面分析（L3-L5 必做）

```bash
python scripts/novel.py --root <root> notes add --chapter 8 --text "<建议原文>" --source user
python scripts/novel.py --root <root> revise plan --chapter 8 --change "<改动>" --out notes/revise-ch8.md
```

输出的四块内容必须逐块读完：

1. **受影响的既有文本**：直接涉及的章节 + 基准章之后的连带章节
2. **受影响的台账**：时间线事件（含 seq）、伏笔、人物
3. **大纲中需要同步的节拍**：这里匹配不到 ≠ 不用改，往往意味着**要新增节拍**
4. **必答四问**：时间线要不要重排 / 要不要补前置 / 伏笔还成不成立 / 算调整还是算偏离

> 关键词没匹配上时，改用更具体的实体名（人物名 / 事件名 / 地点名）重试一次，
> 仍匹配不到就手动扫一遍 `timeline show` 和 `foreshadow list`。

---

## 三、两套方案，都要写出来

**方案甲 · 最小改动**
- 只改本章与直接冲突处，其余靠补叙 / 追认弥合
- 成本低、风险低，代价是可能留疤（细心的读者能感到别扭）
- 适合：连载中、更新压力大、改动不涉及核心因果

**方案乙 · 彻底重排**
- 从基准章起重排 time line 与因果链，改写范围大但自洽
- 适合：改动触及核心动机 / 身份 / 关键人物生死

两份都要写清：**改写范围（哪几章）、新增/删除哪些节拍、需要补哪些前置、预计新增字数**。
然后用 `AskUserQuestion` 让用户选 —— 剧情走向的决定权在作者，不在助手。

## 四、连锁同步表（改完之后逐项打钩）

改完正文不等于改完。**这张表没走完，`check --all` 一定还有债。**

| 改动内容 | 必须同步的台账 | 命令 |
|---|---|---|
| 人物生死/状态变化 | 时间线事件 + effect | `timeline add --effect 角色.status=dead` |
| 人物所在地变化 | 时间线事件 location | `timeline add --location` |
| 人物获知某事 | 知情边界 | `character knows --id --events ev00X` |
| 事件顺序调整 | 事件 seq 重排 | `timeline add --seq` |
| 事件删掉 | 删除事件 + 检查依赖它的伏笔 | 手工编辑 `timeline.json` |
| 伏笔改埋设位置 | `planted_chapter` | `foreshadow add`（重建）+ 删旧 |
| 伏笔改回收位置 | `due_chapter` / `resolve` | `foreshadow resolve --id --chapter N` |
| 大纲节拍增删 | `outline.md` + sync | 改文件后 `sync` |
| 偏离大纲 | 偏离记账 | `mark-beat --status deviated --nature ...` |
| 名词改主称呼 | glossary | `glossary add --main ... --aliases ...` |

同步完跑：

```bash
python scripts/novel.py --root <root> sync && python scripts/novel.py --root <root> check --all
```

## 五、章节改写指令模板

把改动交给执行时（无论是自己写还是派给子代理），用这个骨架：

````
## 任务
按下面的修改建议改写第 N 章。

## 原文位置
文件：<chapters/ch00N.md>
涉及段落：<第几节 / 大致位置>

## 修改建议（原文）
<用户原话>

## 已确认的方案
<甲 / 乙>，用户已确认。

## 影响面（必须先读）
- 直接受影响章节：<...>
- 受影响的时间线事件：<...>
- 受影响的伏笔：<...>
- 需要同步的大纲节拍：<...>

## 本章原有节拍（不得整体丢弃）
- <节拍 1>
- <节拍 2>

## 硬约束
1. 视角与时保持不变：<...>
2. story-time 区间：seq <start>–<end>，不得倒流
3. 角色知情边界：<角色> 不知道 <事件>
4. 未到期伏笔不得提前回收

## 交付
1. 改写后的正文（写回原文件）
2. 列出你改了哪几处、每处一句话理由
3. 列出需要同步的台账项（按连锁同步表）
````

## 六、改完之后的复核

1. `check --all` —— P0 清零
2. `relapse_check.py count` —— 改过的数字在全书还是同一个吗（本手册第四节同步完才跑）
3. `report` —— 出一份报告，确认没有新增债务
4. 若改动属 **beneficial 偏离** → 把新走向写进 `outline.md`，让它成为契约
5. 若属 **harmful 偏离** → 记进 `notes`，排进下一轮修订
6. 把这条建议 `notes resolve --id n00X`，闭环

---

## 七、与审校衔接

审校团（阅稿堂）给出的意见，落到本工程的方式：

1. 每条意见 → `notes add --chapter N --text "..." --source review`
2. 按上面的分类表分级，L4/L5 走影响面分析
3. 改完走连锁同步表 + 复核
4. 闭环时 `notes resolve`

这样审校结论不会散落在聊天记录里，而是变成可追踪、可关闭的修订任务。
